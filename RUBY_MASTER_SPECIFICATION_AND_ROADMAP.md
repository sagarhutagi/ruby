# 0. Execution contract

1.  Inspect the current working directory before changing anything.
2.  Never overwrite an existing project or user data without explicit
    permission.
3.  Create `ARCHITECTURE.md`, `ROADMAP.md` and `TASKS.md` before
    substantial implementation.
4.  Follow the locked decisions in this specification. Do not substitute
    technologies casually.
5.  Implement in phases. Keep the application runnable at the end of
    every phase.
6.  Run tests and fix failures before marking a task complete.
7.  Do not use fake statistics, fake providers, placeholder buttons or
    mock functionality in production paths.
8.  Never claim a feature works until it has been exercised and tested.
9.  If a feature cannot be implemented reliably, document the limitation
    and provide a safe fallback.
10. Maintain `TASKS.md` with completed, in-progress, blocked and pending
    work. Include exact next steps before ending a work session.
11. Do not execute arbitrary shell commands generated by an LLM or found
    in uploaded documents.
12. Never silently send local documents or private content to a cloud
    provider.
13. Prefer simple, maintainable solutions over unnecessary
    infrastructure.

# 1. Product definition

**Name:** Ruby\
**Description:** A local-first, AI-powered academic intelligence and
knowledge management system.

Ruby combines: - NotebookLM-style document intelligence. -
Obsidian-style knowledge management. - ChatGPT-style conversational
interaction. - Anki-style flashcards and spaced repetition. - Academic
tutoring and examination preparation. - Persistent, user-controlled AI
memory. - Local and cloud AI provider integrations. - System and
resource monitoring.

The initial target is a single-user application running locally on
Linux, especially Arch Linux and CachyOS.

Primary goals: 1. Import and understand academic resources. 2. Answer
questions using one or more uploaded resources. 3. Maintain useful,
inspectable long-term memory. 4. Generate notes, quizzes, flashcards and
mock examinations. 5. Organise knowledge by subjects, collections and
concepts. 6. Allow users to configure and switch AI providers
dynamically. 7. Show which resources, models and sources are used. 8.
Protect user data and make cloud usage explicit.

# 2. Locked architecture decisions

Do not replace these decisions without identifying a genuine technical
incompatibility and documenting it.

## Architecture style

Use a **modular monolith**, not microservices.

Components: - One React frontend. - One FastAPI backend. - Background
jobs managed by the backend. - One SQLite relational database. - One
persistent ChromaDB vector store. - SQLite FTS5 for keyword search. -
Local filesystem for original documents and generated artifacts. -
Clearly separated modules communicating through interfaces.

Do not introduce PostgreSQL, Redis, Kafka, Kubernetes or distributed
services. They are unnecessary for the initial single-user application.

## Frontend

-   React 19
-   TypeScript
-   Vite
-   Tailwind CSS
-   shadcn/ui
-   Lucide React
-   TanStack Query for server state
-   Zustand for client state
-   React Router
-   Recharts for analytics
-   React Flow for knowledge graph visualisation

## Backend

-   Python 3.12+
-   FastAPI
-   Pydantic v2
-   SQLAlchemy 2
-   Alembic migrations
-   asyncio
-   HTTPX

Use async endpoints for I/O. Move CPU-heavy parsing, OCR, embedding and
other blocking work into background workers or thread/process execution
as appropriate. Never block the event loop with heavy synchronous
operations.

## Persistence

-   SQLite: primary application database.
-   ChromaDB: persistent vector storage.
-   SQLite FTS5: full-text keyword index.
-   Filesystem: original documents, extracted artifacts, exports and
    backups.

Keep originals separate from extracted text, chunks, embeddings and
generated files. Make the data directory configurable and exclude it
from Git.

## AI infrastructure

-   Ollama for local inference.
-   Official SDKs for cloud providers where available.
-   HTTPX for OpenAI-compatible APIs.
-   Sentence Transformers for local embeddings.
-   Configurable reranking models.
-   Independent provider adapters and capability declarations.

## Local URLs

Development: - Frontend: `http://127.0.0.1:5173` - Backend:
`http://127.0.0.1:8000`

Production: FastAPI should serve the built frontend.

Bind to localhost by default. Remote/LAN access must require explicit
user configuration and appropriate security controls.

# 4. Dynamic AI provider manager

This is a critical subsystem. Ruby must not be tied to one AI vendor or
one model.

Create a provider abstraction with capability declarations. Distinguish
chat generation, embeddings, reranking, vision and CLI execution; not
every provider/model supports every capability.

## Required provider integrations

1.  Ollama.
2.  OpenAI.
3.  Google Gemini.
4.  Anthropic Claude.
5.  OpenRouter.
6.  Generic OpenAI-compatible endpoints.
7.  External AI command-line tools through a separate integration
    subsystem.

## Provider configuration

Configure through the GUI: - Display name. - Provider type. - Base
URL. - API key or credential reference. - Model identifier. - Timeout. -
Temperature. - Maximum output tokens. - Context window. -
Provider-specific settings. - Enabled/disabled state.

Support adding, editing, testing, switching and removing providers
without code changes.

## Ollama

Implement: - Server endpoint configuration and connection testing. -
Model listing and metadata. - Model availability and running status. -
Pull/download and delete model actions. - Model selection and generation
settings. - Clear errors when Ollama is unavailable.

Use Ollama's documented API. Do not assume every model supports vision,
tools, JSON mode or other capabilities.

## Cloud providers

Implement: - Credential validation. - Model selection and model
discovery where supported. - Streaming. - Timeout and retry handling. -
Usage/token reporting where available. - Cost estimates only when
reliable pricing data is available.

Clearly indicate when a request leaves the machine. Never silently fall
back from local to cloud inference.

## CLI integrations

Keep CLI tools separate from API providers. Support configurable
executable path, arguments, working directory, environment variables,
timeout and permissions.

Integrate Antigravity CLI only through its documented or discoverable
executable interface. Do not pretend it is a generic HTTP API. Use safe
subprocess handling, avoid shell interpolation, and require approval for
destructive or external actions.

## Model routing

Allow separate models for: - Main chat. - Complex reasoning. -
Embeddings. - Reranking. - Summarisation. - Flashcard generation. - Quiz
generation. - Document/vision processing.

Show active provider and model. Allow explicit user-configured fallback
only. Never switch to a cloud provider silently.

## Secret handling

-   Never expose API keys to frontend responses.
-   Never log credentials.
-   Prefer Linux Secret Service / OS keyring.
-   Provide a documented encrypted fallback if keyring is unavailable.
-   Mask secrets in the UI.
-   Support credential replacement and removal.
-   Support environment variables for deployment.
-   Do not store plaintext API keys in SQLite.

# 5. Hardware-aware inference

Initial target machine: - NVIDIA RTX 3050 Laptop GPU, 6GB VRAM. - 24GB
system RAM. - 512GB NVMe SSD. - CachyOS / Arch Linux.

Implement real monitoring for: - GPU name. - GPU VRAM total and used. -
GPU utilisation. - System RAM. - CPU utilisation. - Disk usage. - Active
inference provider. - Model loading and inference status.

Use NVML or `nvidia-smi` where available. Gracefully report unavailable
metrics rather than inventing values.

Provide model memory warnings and practical suggestions for quantised
4B--8B models, context limits and CPU/GPU offloading when supported. Do
not assume an installed model fits in VRAM. Avoid loading multiple large
models concurrently by default.

# 6. Universal document ingestion

## Supported formats

Documents: - PDF, including scanned PDFs. - DOCX and DOC where reliable
conversion is available. - PPTX and PPT where reliable conversion is
available. - XLSX, XLS and CSV. - TXT, Markdown, HTML, JSON, XML and
EPUB.

Images: - PNG, JPG, JPEG, WEBP and TIFF.

Use format-specific parsers: - PyMuPDF for PDF. - python-docx for
DOCX. - python-pptx for PPTX. - openpyxl for Excel. - pandas for tabular
data. - BeautifulSoup for HTML. - Tesseract for OCR. - Suitable EPUB
parsing library.

For legacy formats, use a safe, optional conversion path (for example
LibreOffice headless) if installed. Clearly report unsupported formats.

## Extract and preserve

-   Text, headings and paragraphs.
-   Tables and their structure.
-   Equations where extractable.
-   Code blocks.
-   Images.
-   PDF page numbers.
-   PowerPoint slide numbers.
-   Excel sheet names and cell ranges.
-   Document metadata.
-   Section/heading locations.

Support optional vision-model processing for image-heavy documents, but
clearly disclose if it uses a cloud provider.

## Ingestion workflow

-   Drag-and-drop upload.
-   Multi-file upload.
-   Folder import and recursive scanning.
-   Batch processing.
-   Automatic type detection.
-   SHA-256 duplicate detection.
-   Metadata extraction.
-   Subject and collection assignment.
-   Custom tags.
-   Processing progress.
-   Cancellation and retry.
-   Re-indexing.
-   Document deletion.
-   Document version tracking.

Use persistent background job records with status, progress, errors and
timestamps. The UI must remain responsive. Jobs should recover safely
after application restart.

Validate file size, MIME/type, extension and content where practical.
Protect against path traversal, malicious archives and malformed files.

# 7. Subjects and collections

Provide editable subject and collection management: - Create, rename and
delete subjects. - Nested collections. - Move documents. - Tags. -
Search and filters. - Cross-subject collections. - Filter by type, date,
subject and indexing state.

Seed optional subject suggestions: - Mathematics. - Data Structures and
Algorithms. - Computer Networks. - Digital Logic and Computer Design. -
Operating Systems.

These must be editable, not mandatory hardcoded categories.

# 8. RAG engine

Build a modular retrieval-augmented generation pipeline:

1.  Ingestion.
2.  Parsing and normalisation.
3.  Structure-aware chunking.
4.  Metadata attachment.
5.  Embedding generation.
6.  Vector indexing.
7.  Keyword indexing.
8.  Query processing.
9.  Retrieval.
10. Reranking.
11. Context assembly.
12. LLM generation.
13. Citation validation.
14. Response delivery.

## Chunking

Support recursive, structure-aware and semantic chunking. Make chunk
size and overlap configurable. Preserve document ID and source location
for every chunk. Avoid splitting tables and code blocks arbitrarily.

## Embeddings

Support configurable embedding models and providers. Initial options
should include BGE-M3 and nomic-embed-text where compatible.

Keep embedding models separate from generation models. Validate vector
dimensions and model compatibility. If an embedding model changes,
rebuild indexes safely without destroying the existing index until the
replacement succeeds.

## Retrieval

Implement: - Vector similarity search. - BM25/keyword search using
SQLite FTS5. - Hybrid search. - Metadata and subject filters. - Document
filters. - Configurable top-k and thresholds. - Reranking.

Use reciprocal-rank fusion or another documented, tested fusion method
to combine vector and keyword results.

Advanced configurable features: - Query rewriting. - Multi-query
retrieval. - Context compression. - Parent-child retrieval. -
Cross-document comparison. - Duplicate-source removal. -
Conversation-aware retrieval.

## Answer modes

1.  **Resource-grounded:** use uploaded resources as evidence.
2.  **General knowledge:** answer using the selected model.
3.  **Hybrid:** combine resource evidence and model knowledge, clearly
    distinguishing them.
4.  **Research:** compare documents, identify agreement and
    disagreement, and cite sources.

If evidence is absent, say so. Do not fabricate citations or present
unsupported model knowledge as document-derived fact.

## Citation requirements

Citations must include the most precise available: - Document title. -
Page number. - Section or heading. - Relevant excerpt. - Source
location.

For PowerPoint, cite slide number. For Excel, cite sheet and cell range.
For DOCX and other formats, cite headings or paragraph locations where
page numbers are unavailable.

Clicking a citation should open the document at the cited location when
supported. Never invent page numbers, excerpts or source locations.
Track citation provenance through parsing, chunking, retrieval and
generation.

# 9. Memory management

Memory is a separate subsystem. Do not equate it with chat history,
document chunks or vector search.

## Memory types

**Working memory** - Current conversation. - Recent messages. -
Temporary instructions. - Active document context.

**Episodic memory** - Previous sessions. - Important discussions. -
Questions asked. - Learning difficulties. - Mistakes and corrections. -
Study progress.

**Semantic memory** - Concepts. - Definitions. - Facts and
relationships. - Subject-specific knowledge.

**User profile memory** - Learning preferences. - Academic goals. -
Preferred explanation style. - Study preferences.

**Procedural memory** - Preferred workflows. - Repeated instructions. -
Problem-solving approaches.

## Memory lifecycle

Implement: 1. Candidate extraction. 2. Importance scoring. 3. Duplicate
detection. 4. Contradiction detection. 5. User approval where
configured. 6. Consolidation. 7. Retrieval. 8. Updating. 9. Expiration
where appropriate. 10. Deletion.

Do not permanently save every user message. Make automatic memory
extraction and approval policy configurable.

## Memory manager UI

Allow: - Browse and search all memories. - Filter by category. - View
creation/update dates. - Inspect source conversation or source event. -
View confidence and provenance. - Edit, delete and pin. - Export and
import. - Disable memory categories. - Inspect audit history.

Deleting a memory must remove its searchable representations and derived
indexes. Keep temporary context and permanent memory clearly
distinguished.

# 16. Security and privacy

Implement: - Localhost-only default binding. - API key protection. -
Input validation. - File upload validation and size limits. - Path
traversal protection. - Safe archive extraction. - SQL injection
prevention through parameterised ORM operations. - XSS prevention. -
Restricted code execution. - Safe subprocess execution. - Secret
redaction. - Configurable network access. - Data export and complete
data deletion.

Treat uploaded documents as untrusted data. Prompt-injection

clear user-facing disclosure.

# 23. First execution instructions

Start by inspecting the working directory and available environment.

Then:

1.  Create `ARCHITECTURE.md`.
2.  Create `ROADMAP.md` by copying and tracking the roadmap above.
3.  Create `TASKS.md` with individual actionable checkboxes.
4.  Create the project structure.
5.  Implement Phase 1.
6.  Run tests and verify startup.
7.  Continue through the roadmap in order.

Do not stop after writing the planning files. Continue implementing.

At the end of each work session, update `TASKS.md` with: - Completed
tasks. - In-progress tasks. - Blocked tasks and the reason. - Tests run
and their results. - Files changed. - Exact next steps.

If context or execution limits interrupt work, leave the repository in a
runnable state and write a precise handoff in `TASKS.md`. Resume from
that handoff rather than restarting or rewriting completed work.

**Final engineering principle:** Prioritise correctness, source-grounded
answers, reliable memory, secure provider integration and
maintainability over visual polish or feature count. Build Ruby as a
cohesive, dependable personal academic intelligence system.
